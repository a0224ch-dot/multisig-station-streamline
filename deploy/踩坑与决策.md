## 1. 开通码 300 秒是旧默认

**现象**  
签名页要先选钱包，5 分钟不够。改了代码默认值后，已安装站点仍表现成 5 分钟；或有人把 `.env` 改回 `300`，以为能恢复短有效期，实际仍是 15 分钟。

**根因**  
安装脚本曾经写死 `OPEN_TOKEN_TTL_SECONDS=300`。在线更新**不覆盖** `.env`，所以只改代码默认值，老站点不会变。`20260916-1` 起把缺省、非法值、以及正好等于 `300` 的旧默认，都按 **900 秒**处理。

**正确做法**  
- 新安装用 `900`（见 `.env.example` 与安装脚本）。  
- 要其它时长，设成**不是 300** 的正整数秒。  
- 签名页应展示 `expiresAt`；过期显示可读说明，不要只甩 `expired`。

**别再怎么做**  
- 不要以为改 `openSession.ts` 的默认值就会改掉现网 `.env`。  
- 不要把 `300` 再写回 `.env` 当「自定义 5 分钟」——代码会当成旧默认。

## 2. 成功页只显示 TxID 不算完成

**现象**  
开通成功只看到 TxID，客户不知道去哪核对权限，也不知道地址还能不能当收款地址。失败时页面只显示 `expired`、`fail`、`broadcast_failed`。

**根因**  
客户可见缺口在签名页文案和错误码翻译，不在链上拒绝翻译函数。未签名交易约 60 分钟、链上拒绝中文原因两边本来就一致，重复改那一层容易带进不该外发的说明。

**正确做法**  
- 成功页给 Tronscan 地址/交易链接，说明如何看「权限 / Permissions」，以及收款不变、转出需共管、手续费、助记词仍要保管。  
- 核对口径写到「多个签名地址且门槛大于 1」即可。中英都要有。  
- 有交易所回跳时仍保留「立即返回」，不要为了加说明删掉回跳。  
- `HELP_DOC_VERSION` 与根目录 `VERSION` 一起改。

**别再怎么做**  
- 不要只改后台使用说明、不改签名页。  
- 不要在成功页或使用说明里写内部档位何时触发。

## 3. 外发文档与 Release 说明不写内部口径

**现象**  
对齐其它站点时，把内部档位、阈值、上游地址来源写进精简版 README、使用说明、help、对外 Release notes。

**根因**  
精简版源码和 OTA 包会到客户手里。打包会带上 `README.md`、`CHANGELOG.md` 和 `deploy/`。

**正确做法**  
- 对外 Release `notes` 只用「修复已知 BUG / 更新功能」，不写功能细项。  
- 内部档位触发条件只留在总部文档，不写进精简版 README、使用说明、help、本文件。  
- CHANGELOG 可以记客户能看见的行为（有效期、成功页、错误码），不要记触发条件。

**别再怎么做**  
- 不要把分公司/总部使用说明整段复制进精简版。  
- 不要用中文细项当 GitHub Release notes。

## 4. Windows 打包缺 esbuild.exe

**现象**  
`bash deploy/pack-release.sh` 或本机 `npm run build` 失败：已安装 `@esbuild/win32-x64`，却提示当前平台也需要 `@esbuild/win32-x64`。

**根因**  
`frontend/node_modules/@esbuild/win32-x64/` 里只有 `package.json`，**没有 `esbuild.exe`**。再跑 `npm install` 会显示 up to date，不会补二进制。与 Git Bash / PowerShell 无关。

**正确做法**  

```bash
cd frontend
rm -rf node_modules/@esbuild/win32-x64
npm install --no-save --force @esbuild/win32-x64@0.21.5
# 确认出现 esbuild.exe 后再打包
```

版本号与 `frontend/node_modules/esbuild/package.json` 的 `version` 对齐。

**别再怎么做**  
- 不要只反复 `npm install`。  
- 不要把缺二进制误判成「Git Bash 平台不对」后改打包脚本。

## 5. zip 打好不等于已发布

**现象**  
本地已有 `dist-release/streamline-版本.zip` 和 `latest.json`，后台「检查更新」仍看不到新版。`gh release create` 报需要 `workflow` scope，直接打 API 却是 **404**。

**根因**  
能读 `a0224ch-dot/multisig-station-streamline-releases` 不等于能建 Release。总部账号 `e12games` 查看旧 Release 可以，创建会 404；`gh` 有时把无权限说成 scope 不足。  
另外：Release 附件和仓根 `latest.json` 是两步。只建 Release、不更新 `main` 上的 `latest.json`，站点清单仍是旧版。

**正确做法**  
- 用对 `a0224ch-dot/multisig-station-streamline-releases` **有写权限**的账号建 Release，tag 等于版本号，附件为 zip。  
- 再把本次 `dist-release/latest.json` 推到该仓 **main 根目录**。`zipUrl` 必须指向 a0224ch-dot 的 download 地址。  
- `20260916-1` 的 zip 曾在本机打出，**尚未上传**。下次发这版前先确认发布仓没有这个 tag；若要带上本文档，先重新打包再传。

**别再怎么做**  
- 不要用只能读 Release 的账号硬发，也不要只 `gh auth refresh -s workflow` 当根因。  
- 不要只传 zip 不改 `latest.json`。  
- 不要把分公司/总部发布仓（e12games）当成精简版更新源。

## 6. 脏工作区会进更新包

**现象**  
更新包里出现尚未定稿的验收清单、友商说明或截图脚本改动。

**根因**  
`pack-release.sh` 复制的是磁盘上的 `deploy/`，不是 git 已提交内容。

**正确做法**  
打包前 `git status`。与本版无关的改动先移开再打 zip，打完再恢复。zip 内容应能对上本版提交。

**别再怎么做**  
- 不要在工作区脏着时打包。  
- 不要把下一阶段的交付文档和本版功能打进同一个未说明的包。

## 7. 在线更新不改 .env

**现象**  
升级后端口、密钥、开通码有效期、发布仓地址和升级前一样；或以为升级会把 `OPEN_TOKEN_TTL_SECONDS` 从 300 改成 900 的字面值。

**根因**  
更新保护 `.env` 和数据库。有效期变化靠代码识别旧默认 `300`，不是靠改写配置文件。

**正确做法**  
升级前抄下 `.env` 里的 `PORT`、`JWT_SECRET`、`BRANCH_API_KEY`、`UPDATE_RELEASES_URL`。升级后核对：配置还在、能用原密码登录、`/api/health` 仍是 `"edition":"streamline"`。有效期以签名页「有效至」为准，不要只看 `.env` 里是否仍写 300。

**别再怎么做**  
- 不要在升级脚本里覆盖 `.env`。  
- 不要把精简版反代指到总部 `8788`。

## 8. `docs/` 被忽略但仍可能打进 zip

**现象**  
踩坑写在 `docs/` 后 `git add` 没进仓库；下次换机器没有这份记录。若本机目录还在，打包时却可能出现在更新包里。

**根因**  
`.gitignore` 把 `docs/` 标成内部备忘、不进 git。旧版 `pack-release.sh` 只要目录存在就会 `cp` 进 zip，两套规则相反。

**正确做法**  
- 可外发的踩坑与检查清单放在 `deploy/`，随仓库提交。  
- 真正不外发的备忘留在 `docs/`，且打包**不要**复制该目录。  
- 内部档位触发条件不要写进 `deploy/` 这份可外发手册。

**别再怎么做**  
- 不要把可检索记录只放在被 gitignore 的目录。  
- 不要用 `git add -f docs/` 把内部备忘推进公开源码。
